## RC-1 — `useradd: UID 1000 is not unique` (16 jobs Build)

### Síntoma

`logs_github/25_Build catalog-svc.txt` (líneas 661-663; patrón idéntico en los
otros 15 logs de Build):

```text
#13 [stage-1 3/4] RUN useradd --system --uid 1000 appuser
#13 0.065 useradd: UID 1000 is not unique
#13 ERROR: process "/bin/sh -c useradd --system --uid 1000 appuser" did not complete successfully: exit code: 4
```

### Causa raíz

Los 16 Dockerfiles Java usan `eclipse-temurin:17-jre` como base. Una versión
reciente de la imagen upstream **ya incluye un usuario con UID 1000**, por lo
que `useradd --system --uid 1000 appuser` choca con un UID existente y aborta
con exit 4. El mismo cambio de imagen rompió el build de los 16 servicios en
paralelo.

### Solución

En los **16** `services/<svc>/Dockerfile` de servicios Java se cambió el UID a
**10001** (número del rango system sin conflictos):

```dockerfile
RUN useradd --system --uid 10001 appuser
```

Alineado con **Kubernetes**: los 16 `services/<svc>/k8s/base/deployment.yaml`
pasaron de `runAsUser: 1000` a `runAsUser: 10001` (el pod debe correr como el
usuario de la imagen; `runAsNonRoot: true` se mantiene).

**No** se tocó `services/frontend` (Alpine `adduser -S appuser -u 1000`: no hay
colisión de UID en Alpine y su manifest ya coincide con `runAsUser: 1000`) ni
`services/auth` (imagen Keycloak, que corre como su usuario interno de UID 1000
— ver RC-2).

Archivos modificados (32 en total):

- Dockerfiles: `analytics-svc`, `api-gateway`, `bff-web`, `cart-svc`,
  `catalog-svc`, `checkout-svc`, `config-service`, `discovery-service`,
  `inventory-svc`, `notification-svc`, `order-svc`, `payment-svc`,
  `recommendation-svc`, `returns-svc`, `search-svc`, `shipping-svc`.
- Manifests: `services/<svc>/k8s/base/deployment.yaml` de los mismos 16.

### Evidencia

- Log: `useradd: UID 1000 is not unique` en `4_Build shipping-svc.txt`,
  `6_Build analytics-svc.txt`, `7_Build recommendation-svc.txt`,
  `8_Build order-svc.txt`, `9_Build config-service.txt`,
  `14_Build notification-svc.txt`, `15_Build payment-svc.txt`,
  `18_Build cart-svc.txt`, `19_Build checkout-svc.txt`,
  `22_Build api-gateway.txt`, `23_Build discovery-service.txt`,
  `24_Build inventory-svc.txt`, `25_Build catalog-svc.txt`,
  `27_Build bff-web.txt`, `33_Build search-svc.txt`, `35_Build returns-svc.txt`.

## RC-2 — Imagen Keycloak `24.0.10` inexistente (Build auth)

### Síntoma

`logs_github/16_Build auth.txt` (líneas 548-562):

```text
#2 ERROR: quay.io/keycloak/keycloak:24.0.10: not found
  25 | >>> FROM quay.io/keycloak/keycloak:24.0.10
ERROR: failed to build: failed to solve: quay.io/keycloak/keycloak:24.0.10: failed to resolve source metadata for quay.io/keycloak/keycloak:24.0.10: quay.io/keycloak/keycloak:24.0.10: not found
```

### Causa raíz

`services/auth/Dockerfile:25` referenciaba `quay.io/keycloak/keycloak:24.0.10`.
Verificado contra el issue oficial del proyecto Keycloak (#32932): **24.0.5 fue
la última imagen OSS compilada para la línea 24.x**; los tags 24.0.6/24.0.7
fueron versionados pero nunca publicados como imágenes Docker, y `24.0.10` no
existe.

### Solución

`services/auth/Dockerfile` — pin a la última imagen real de la línea 24:

```dockerfile
FROM quay.io/keycloak/keycloak:24.0.5
```

El `deployment.yaml` de auth conserva `runAsUser: 1000`: es el UID del usuario
`keycloak` dentro de esa imagen (comentado en el propio manifest), no el UID de
temurin, por lo que RC-1 no aplica.

### Evidencia

- Log: `16_Build auth.txt`, líneas 548-562 (`not found` + trace de buildx).

## RC-3 — Falta `spring.config.import` en 4 configs de test

### Síntoma

`logs_github/1_Test api-gateway.txt` (línea 298; idéntico en
`17_Test inventory-svc.txt` línea 1501 y `28_Test bff-web.txt` línea 1439):

```text
2026-09-09T23:05:26.6444679Z No spring.config.import property has been defined
...
Caused by: org.springframework.cloud.commons.ConfigDataMissingEnvironmentPostProcessor$ImportException: No spring.config.import set
```

### Causa raíz

Misma mecánica documentada en [02-config-import.md](02-config-import.md):
`src/test/resources/application.yml` sombrea al de `src/main/resources/` en el
classpath de Maven, el `spring.config.import` del config server nunca llega al
entorno de test y el `ConfigDataMissingEnvironmentPostProcessor` aborta el
arranque. En la corrida anterior se arreglaron 10 servicios; estos 4
(`api-gateway`, `inventory-svc`, `bff-web` y `analytics-svc` — este último
enmascarado por el error de compilación de RC-4) quedaron pendientes.

### Solución

Se replicó el patrón exacto ya establecido en los 10 servicios arreglados, en
cada `services/<svc>/src/test/resources/application.yml`:

```yaml
spring:
  cloud:
    config:
      import-check:
        enabled: false
```

- `api-gateway`: bloque `spring:` nuevo.
- `inventory-svc`: fusionado con el bloque `spring:` existente (datasource H2).
- `bff-web`: bloque `spring:` nuevo (antes de `bff:`).
- `analytics-svc`: bloque `spring:` nuevo.

No se tocó ningún `src/main/resources/application.yml` (el runtime sigue
importando el config server).

### Evidencia

- Logs: `1_Test api-gateway.txt:298/383`, `17_Test inventory-svc.txt:1501/1586`,
  `28_Test bff-web.txt:1439/1524` (`APPLICATION FAILED TO START` +
  `ImportException`).

## RC-4 — Error de compilación `comparingByValue` en analytics-svc

### Síntoma

`logs_github/5_Test analytics-svc.txt` (líneas 169-174):

```text
[ERROR] COMPILATION ERROR :
[ERROR] /home/runner/work/K8s/K8s/services/analytics-svc/src/main/java/com/ecommerce/analytics/service/AnalyticsService.java:[73,35] cannot find symbol
  symbol:   method <java.util.Map.Entry<java.lang.Long,java.util.concurrent.atomic.AtomicLong>>comparingByValue(java.util.Comparator<java.util.concurrent.atomic.AtomicLong>)
[ERROR] 1 error
[INFO] BUILD FAILURE
```

### Causa raíz

`AnalyticsService.topProducts()` llamaba a
`Comparator.<Map.Entry<Long, AtomicLong>>comparingByValue(...)`. El método
`comparingByValue` **no es estático en `Comparator`**: es un estático de
`Map.Entry` (`Map.Entry.comparingByValue(Comparator<? super V>)`). Al invocarlo
sobre la clase equivocada, javac reporta `cannot find symbol`.

### Solución

`AnalyticsService.java:73` — mover la invocación a la clase correcta (import
`java.util.Map` ya existente; comportamiento idéntico):

```java
.sorted(Map.Entry.<Long, AtomicLong>comparingByValue(
                Comparator.comparingLong(AtomicLong::get))
        .reversed()
        .thenComparing(Map.Entry::getKey))
```

Sigue ordenando por conteo descendente (con el comparador `AtomicLong::get`) y
desempata por id de producto.

### Evidencia

- Log: `5_Test analytics-svc.txt:171-174` (`cannot find symbol` + `1 error`).
- Fix verificado por lectura de tipos/imports (sin Maven local).

## RC-5 — Aserciones de tamaño sobre un store compartido (catalog y order)

### Síntoma

`logs_github/12_Test catalog-svc.txt` (líneas 1536-1540) y
`logs_github/32_Test order-svc.txt` (líneas 1537-1541):

```text
[ERROR] com.ecommerce.catalog.CatalogServiceApplicationTests.seededProductsAreListed ... FAILURE!
java.lang.AssertionError: Expected size: 4 but was: 5 in: [...]
[ERROR] com.ecommerce.order.OrderServiceApplicationTests.seededOrdersAreListed ... FAILURE!
java.lang.AssertionError: Expected size: 2 but was: 3 in: [...]
```

### Causa raíz

Los tests ejecutan sobre un **mismo contexto** de aplicación con H2 compartido
y el orden de métodos de JUnit 5 no está garantizado:

- catalog: el seed carga **4** productos (evidencia en el propio log:
  `DataSeeder: Seeded 4 demo products`, línea 1531). El round-trip
  `createThenGetProductRoundTrips` crea un 5.º ("Webcam HD-720", id=5). Si
  `seededProductsAreListed` corre después, el listado devuelve 5 y el `hasSize(4)`
  falla.
- order: el seed carga **2** órdenes (`Seeded 2 sample orders`, línea 1531).
  `createThenGetOrderRoundTrips` crea una 3.ª (cust-99, id=3). Si
  `seededOrdersAreListed` corre después, devuelve 3 y el `hasSize(2)` falla.

No es un problema del seed ni un bug de los servicios: es **dependencia de
orden** entre tests que comparten estado. Arreglar el seed o subir la cifra
esperada solo trasladaría el flakiness.

### Solución

Ambos tests pasan de asumir un tamaño absoluto a **asertar presencia** de los
registros sembrados (misma fuerza, independiente del orden):

- `catalog-svc/.../CatalogServiceApplicationTests.seededProductsAreListed`:
  extrae los nombres y verifica que estén los 4 del seed (`Wireless Mouse
  MX-10`, `Mechanical Keyboard K87`, `27" IPS Monitor`, `USB-C Docking
  Station`).
- `order-svc/.../OrderServiceApplicationTests.seededOrdersAreListed`: extrae
  los `customerId` y verifica que estén `cust-42` y `cust-7`.

Las demás aserciones (404, round-trip, `ordersAreQueryableByCustomer` por
cliente) ya eran deterministas y no se tocaron.

### Evidencia

- Logs: `12_Test catalog-svc.txt:1536-1545` y `32_Test order-svc.txt:1537-1545`
  (payloads mostrando el 5.º producto / 3.ª orden creados por el round-trip).

## RC-6 — Tests de search-svc contra asunciones stale del scoring

### Síntoma

`logs_github/30_Test search-svc.txt` (líneas 1393-1406):

```text
[ERROR] SearchServiceApplicationTests.categoryFilterRestrictsResults:48 ... FAILURE!
Expecting actual not to be empty
[ERROR] SearchServiceApplicationTests.nameMatchScoresHighest:38 ... FAILURE!
expected: 3.0
 but was: 4.0
```

### Causa raíz

- `nameMatchScoresHighest`: el test asumía score 3.0 (solo name). Pero la regla
  documentada en `docs/casos-de-uso/sistema-ecommerce.md` es **aditiva por
  campo**: nombre = 3, descripción = 1, tag = 1. El teclado K87 matchea
  nombre ("keyboard") **y** tag ("keyboard") → 4.0 legítimo. El código es
  correcto; la asunción del test ignoraba el tag.
- `categoryFilterRestrictsResults`: el query `hd` con `category=Audio` no
  matchea **nada** en Audio: el único producto Audio (`Bluetooth Headset NC`)
  no contiene "hd" en nombre (`Bluetooth Headset NC`), descripción
  (`Over-ear, active noise cancelling`) ni tags (`headset`, `bluetooth`,
  `noise-cancelling`). El filtro por categoría **funciona correctamente**; el
  comentario del test (`"'hd' only matches a description/tag of the headset"`)
  era falso.

### Solución

Se corrigieron las **asunciones del test** (el código cumple la regla
documentada, que queda como autoridad):

- `nameMatchScoresHighest`: expectativa 3.0 → **4.0**, con comentario que
  documenta la suma nombre(3) + tag(1) según la regla de
  `sistema-ecommerce.md`.
- `categoryFilterRestrictsResults`: query `hd` → **`noise`** (matchea
  descripción "active noise cancelling" y tag "noise-cancelling" del headset,
  único hit en Audio). Se conserva el bucle que verifica que todos los
  resultados pertenezcan a `Audio`.

### Evidencia

- Log: `30_Test search-svc.txt:1393-1406`.
- Regla documentada: `docs/casos-de-uso/sistema-ecommerce.md` línea 55
  (`Ranking con scoring: nombre=3, descripción=1, tag=1`).

## RC-7 — Trivy: HIGH en actuator (CVE-2026-22733) y pgjdbc

### Síntoma

`logs_github/13_Trivy filesystem scan.txt` (líneas 220-280): 4 hallazgos HIGH,
con `exit code 1` y `Total: 4 (HIGH: 4, CRITICAL: 0)`:

```text
org.springframework.boot:spring-boot-starter-actuator  CVE-2026-22733  HIGH  fixed  3.3.5  4.0.4, 3.5.12
org.postgresql:postgresql                             CVE-2025-49146  HIGH  fixed  42.7.4  42.7.7
org.postgresql:postgresql                             CVE-2026-42198         fixed  42.7.4  42.7.11
org.postgresql/postgresql (scram-client)              CVE-2026-54291         fixed  42.7.4  42.7.12
```

### Causa raíz

- El driver `org.postgresql:postgresql` se resolvía a **42.7.4** desde el
  parent `spring-boot-starter-parent:3.3.5` (sin `<version>` explícita en los
  4 poms que lo declaran), y 42.7.4 tiene 3 CVEs.
- `spring-boot-starter-actuator:3.3.5` (versión gestionada por el mismo parent)
  tiene CVE-2026-22733 (auth bypass en el endpoint CloudFoundry de Actuator).
  El fix OSS existe solo en **Spring Boot 3.5.12** (verificado en
  spring.io/security/cve-2026-22733), un bump de línea mayor con riesgo de
  compatibilidad con Spring Security / Spring Cloud 2023.0.3.

### Solución

1. **pgjdbc → 42.7.13** (última release 42.7.x en Maven Central; cubre los tres
   CVEs: 49146→42.7.7, 42198→42.7.11, 54291→42.7.12). Se agregó `<version>`
   explícita en los 4 poms con dependencia `postgresql` (no hay parent de
   proyecto compartido):
   - `services/catalog-svc/pom.xml`
   - `services/inventory-svc/pom.xml`
   - `services/order-svc/pom.xml`
   - `services/payment-svc/pom.xml`

2. **`.trivyignore` en la raíz del repo** — solo para CVE-2026-22733, con
   justificación: los servicios no exponen ni usan el endpoint CloudFoundry de
   Actuator (solo `/actuator/health` para probes), el fix OSS exige 3.5.12 y está
   planificado como follow-up. Nada más se ignora.

El workflow de Trivy honra el archivo: `trivy fs` se ejecuta con `scan-ref: .`
desde la raíz del repo y `trivy-action` no pasa `--ignorefile` ni
`trivyignores` (verificado en el log: `-y` vacío), por lo que Trivy usa el
`.trivyignore` por defecto del directorio actual — la raíz del repo.

### Evidencia

- Log: `13_Trivy filesystem scan.txt:206-280` (command line de trivy + tabla de
  hallazgos).
- Versiones: `https://repo1.maven.org/maven2/org/postgresql/postgresql/maven-metadata.xml`
  (release 42.7.13).
